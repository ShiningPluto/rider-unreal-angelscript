# TODO: use Rider's C++ index for navigation

Deferred deliberately. This records what was found so the work does not have to be re-investigated,
and so nobody starts it expecting it to solve a problem it cannot solve.

## What happens today

"Go to declaration" on an AngelScript symbol that maps to C++ runs in two stages, in
`AngelScriptCppNavigationHandler`:

1. **Which C++ symbol is this?** — asks the language server via `angelscript/getCppSymbol`, which
   returns a `(className, symbolName)` pair.
2. **Where does it live?** — resolved entirely in Rider, by `FilenameIndex` lookups and text search
   over the headers (`AngelScriptLspSettings.CppNavigationStrategy.TEXT_SEARCH`), or delegated to
   the Unreal editor to open in an external IDE (`UNREAL_ENGINE`).

Stage 2 is the weak one. It matches on file names and text, so it has no notion of overloads,
namespaces, or which declaration actually corresponds to the symbol.

## Why it is worth doing

Stage 2 should use the real C++ symbol table instead of text search. Rider parses the Unreal C++
sources anyway, including the UE reflection macros, so the information is already there.

The plumbing is scaffolded but unused:

- `src/dotnet/` is an empty shell: `IAngelscriptRiderPluginZone` declares a zone and imports
  `JetBrains.ReSharper.Psi.CSharp` — **C#, not C++**. Nothing queries any PSI.
- The `:protocol` Gradle module (`settings.gradle.kts`) builds as `NO-SOURCE`. The frontend/backend
  RD protocol has no model defined.

So the work is: define an RD protocol call, implement the backend query against ReSharper C++ PSI,
and have `AngelScriptCppNavigationHandler` use it in place of the text search. Note that the
ReSharper C++ PSI lives behind its own zone, which the plugin does not currently require.

## What it will *not* fix

**It does not make navigation work without a running Unreal editor.**

Stage 1 depends on the language server having resolved the module, which requires the C++ type
database, which only a running Unreal editor can produce. Without it `getCppSymbol` returns null
and stage 2 is never reached. A better stage 2 improves accuracy, not availability.

The type database cache (see `AngelScriptUnrealStatusService` and the cache patch in
`scripts/bundle-lsp.js`) is what addresses availability, and it already covers this case.

## Why the type database cannot be derived from C++ sources instead

This was considered and rejected. The database is not a mirror of the C++ API; it is a projection of
C++ into AngelScript that is *generated by running engine code*. Measured against
`Engine/Plugins/Angelscript` of a real UE5 Angelscript fork:

| | |
|---|---|
| `.cpp` files in the plugin | 686 |
| files containing `FAngelscriptBinds::` | 119 |
| `BindGlobalFunction` calls | 722 |
| ... with a string-literal signature | 624 |
| ... with a signature built at runtime | 98 |

The 98 are decisive. For example, in `Bind_UActorComponent.cpp`:

```cpp
FString FuncDecl = FString::Printf(
    TEXT("%s Get(const AActor Actor, const FName& WithName = NAME_None) no_discard"), *ClassName);
FAngelscriptBinds::BindGlobalFunction(FuncDecl, ...);
```

This iterates the project's component classes and emits one overload per class. The resulting API
surface depends on which modules and plugins were loaded in that run. Even the 624 literals are
AngelScript declaration syntax (`?&` for variable-type parameters, `no_discard`, default arguments),
with no C++ equivalent to parse.

Reflection-derived members (`UPROPERTY`/`UFUNCTION` plus `ScriptName`, `ScriptMethod`, `ScriptMixin`
meta) *are* declarative and could be recovered from headers. That is one of three sources, and
splicing a partial synthetic database into the real one would produce diagnostics that are wrong in
both directions — worse than having none.
